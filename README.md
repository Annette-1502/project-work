# Gold Thief Project Work

## 1. General Explanation of the Problem

The project is based on a graph problem generated by the provided `Problem` class. Each instance contains a set of cities, where city `0` is the depot and all other cities contain a certain amount of gold. The thief must start from the depot, collect all the gold, and eventually return to the depot.

The output of the solution must be a path in the form:

```python
[(0, 0), (c1, g1), (c2, g2), ..., (0, 0)]
```

where each pair contains the city visited and the amount of gold collected there. A key constraint is that every consecutive movement in the returned path must correspond to a real edge in the graph. It is not enough for two cities to be connected by a shortest path: if the final output contains a direct step from city `a` to city `b`, then the edge `(a, b)` must actually exist.

The cost of moving from city `i` to city `j` while carrying `g` gold is:

```text
cost = d_ij + (alpha * d_ij * g) ** beta
```

The value of `beta` changes the nature of the problem. When `beta == 1`, carrying gold has a linear effect. When `beta > 1`, the cost grows in a convex way, so carrying a large amount of gold becomes much more expensive. The goal is to return a valid path with a total cost lower than the baseline method provided in `Problem.py`.

## 3. How I Solved the Problem

The solution is implemented in `src/implementation.py`, inside the function `build_collection_plan`. The required function in `s338906.py` simply calls it:

```python
def solution(p: Problem):
    return build_collection_plan(p)
```

The strategy used is a problem-specific heuristic optimization approach. It does not try to enumerate all possible paths, because the search space is too large. Instead, it builds good feasible solutions and then improves them using ideas studied: constructive greedy heuristics, savings-based decisions, randomized multi-start exploration, and local search. In this sense, the method balances exploration and exploitation: random perturbations generate different candidate route structures, while local improvements refine the best solutions found.

More specifically, the solver can be seen as a combination of three phases:

1. A constructive phase, where an initial feasible solution is created from simple depot-based routes.
2. An exploration phase, where alternative route combinations are generated through sweep constructions and randomized savings.
3. An exploitation phase, where the current best solution is improved through local changes such as moving or swapping cities between routes and reordering cities inside a route.

The algorithm first reads the graph, the values of `alpha` and `beta`, and the amount of gold in each city. It also computes the shortest paths from the depot to all other cities. These shortest paths are not returned directly as a logical shortcut; they are later expanded into real graph edges when the final path is built.

The solver treats the two main cases differently.

For `beta > 1`, the carrying cost is convex. This means that carrying too much gold at once quickly becomes expensive. For this reason, the solver uses repeated depot-city-depot trips and may split the gold of a city into smaller chunks. The number of chunks is estimated by balancing the extra travel distance against the saving obtained by carrying a lighter load. A high but finite chunk limit is used, so the solver can strongly reduce the transported load while still keeping the returned path manageable. This strategy is very effective for convex instances, as shown by the results.

For `beta == 1`, the cost is linear. In this case, splitting gold into many small chunks is not as useful, so the solver builds routes containing multiple cities. The process is:

1. Start from a baseline where each city is visited in an independent route.
2. Compute promising merge candidates using a savings criterion.
3. Build an initial solution by greedily merging routes only when the total route cost improves.
4. Add alternative route constructions using an angular sweep around the depot.
5. Add randomized multi-start attempts by slightly perturbing the savings values.
6. Improve the best routes through local search, mainly by relocating cities between routes. On large dense graphs, this phase is allowed to run a little deeper because those instances showed more room for improvement.
7. Try a small swap-based local search step between route pairs on large graphs when `beta >= 1`.
8. Improve the internal order of some routes with small 2-opt-like reversals and insertion moves.
9. Expand the selected logical routes into a real admissible path over existing graph edges.
10. Delay gold collection in the linear case when collecting later is not worse.
11. Validate the final path before returning it.

The final validation checks that the path starts and ends at `(0, 0)`, uses only existing graph edges, and collects exactly the amount of gold present in every city.

## 5. Considerations

The algorithm performs especially well when `beta > 1`, because the convex cost makes load splitting very effective. In those cases, the improvement over the baseline is consistently very high. The trade-off is that the returned paths become longer, because the thief deliberately performs many lighter trips instead of carrying large loads.

For `beta == 1`, the improvement is smaller because the baseline is already fairly competitive and the carrying cost is only linear. In that setting, the route-based heuristic still improves the baseline, but the margin is naturally narrower.

The extended tests also include two concave cases with `beta < 1`. The solver does not use a separate branch for them, but the route-based strategy still remains valid and improves the baseline in both cases.

The current implementation deliberately avoids being overly complex. Earlier versions included more advanced refinements, but the final version was simplified to keep the method easier to understand and explain. The final approach is based on constructive heuristics, randomized multi-start, and local search, which are coherent with the techniques studied in Computational Intelligence.

The most important correctness point is that the returned path is always expanded over real graph edges. This avoids the common mistake of using shortest-path distances during optimization but returning invalid direct jumps in the final solution.
